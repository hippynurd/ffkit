Copy-First FFmpeg

The methods that run at the speed of copying a file, why each flag is where it is, where each one breaks, and the popular wrong way. Written for people and for the coding agent doing the batch work.

Principles

Stream copy by default. Re-encode only when the output must differ from the input, and then exactly once.

  1. A correct pipeline runs at disk speed. If a cut, join, mux, or container swap is running at 1–5× realtime, it is wrong, not slow. The decoder and encoder should not be in the path.
  2. Probe before you act. Codec, size, frame rate, pixel format, audio layout, keyframe spacing (GOP), and whether the frame rate is variable decide which method is legal. Guessing is how you get a re-encode you didn't ask for.
  3. -ss goes before -i. Before: the demuxer seeks straight to the keyframe. After: ffmpeg decodes from the start of the file to the cut point and throws it all away.
  4. Concat only matches. Same codec, resolution, fps, pixel format, audio codec, sample rate, channels, and constant frame rate. Fix the mismatched clips, not all of them.
  5. Audio problems are not video problems. Missing or mismatched audio gets fixed with the video stream copied. Never re-encode pixels because of a sample rate.
  6. One encode per pipeline, as early as possible. When something must decode (mismatched sources, VFR, filters, a timelapse), do it once to a mezzanine and make every later step copy-only.
  7. Hardware for the one encode you're allowed. On Apple Silicon, -hwaccel videotoolbox before -i and h264_videotoolbox / hevc_videotoolbox / prores_videotoolbox out. Check that the encoder actually works on the machine; a listing isn't proof.
  8. Verify with ffprobe. Exists, non-empty, expected streams, duration within tolerance. The command exiting 0 is not the same as the file being right.
  9. Sources are read-only. Intermediates in work/, deliverables in out/, mezzanines in out/mezzanine/.

Probe

read only

Know what you have before deciding what to do with it. Every other method here depends on something this tells you.

Command

ffprobe -v error -show_format -show_streams -print_format json in.mp4

# keyframe spacing (GOP) over the first 600 frames; "1" marks a keyframe
ffprobe -v error -select_streams v:0 -show_entries frame=key_frame \
        -read_intervals %+#600 -of csv=p=0 in.mp4

What to read off it

  • codec_name h264 / hevc / prores. Clips with different codecs cannot be concat-copied.
  • width × height and pix_fmt. All must match for concat.
  • avg_frame_rate vs r_frame_rate. When they disagree by more than ~2%, the file is variable frame rate.
  • GOP the median gap between keyframes. Decides how far a copy-trim can miss, and whether keyframe-only decode gives the timelapse ratio you want.
  • rotation phone footage carries a rotation tag; copy preserves it, some filters drop it.

Breaks when

  • nb_frames is missing on some containers (MKV, MPEG-TS). Estimate from fps × duration or count frames with -count_frames (slow).
  • Reading GOP on a whole 2-hour file takes a while; sample the first few hundred frames.

ffkit: ffkit probe clip1.mp4 clip2.mov prints one line per file with codec, size, fps, duration, GOP, and a VFR flag.

Trim

copy

Cut a range out of a clip without touching the pictures. Runs in well under a second for any length of file.

Command

ffmpeg -ss 0:10 -i in.mp4 -t 70 -map 0 -c copy \
       -avoid_negative_ts make_zero -movflags +faststart out.mp4

Why it's written this way

  • -ss before -i seeks the demuxer to the keyframe at or before 0:10. No decoding of the first ten seconds.
  • -t 70 duration, not end time. (-to after the input is also fine; mixing -ss-before with -to has changed behaviour across versions, so prefer -t.)
  • -map 0 keep every stream, including subtitles and data tracks ffmpeg would otherwise drop.
  • -c copy no decoder, no encoder. The whole point.
  • -avoid_negative_ts make_zero copy-cuts start on a keyframe before your -ss; this shifts timestamps so the file starts at zero and players don't show a black lead-in or desync.
  • -movflags +faststart moves the MP4 index to the front so playback starts before download finishes. Free.

Breaks when

  • You need a frame-accurate cut. Copy lands on the previous keyframe, so the clip can start up to one GOP early (one to two seconds on phone and action-cam footage). For exact cuts, re-encode once: -ss before -i for the fast seek, then -c:v libx264 -crf 18 -c:a copy.
  • Audio and video keyframes don't line up; a few frames of audio may lead the picture at the cut. make_zero handles most of it.

The wrong way (still ranks first on Stack Overflow)

ffmpeg -i in.mp4 -ss 0:10 -t 70 -c:v libx264 out.mp4

-ss after -i decodes from the start of the file to 0:10 before it writes anything, and -c:v libx264 then re-encodes every frame. Frame-accurate, yes, but two orders of magnitude slower and a generation of quality lost, for a cut that didn't need either.

ffkit: ffkit trim in.mp4 out.mp4 -s 0:10 -e 1:20; add --exact only when you need frame accuracy.

Concat

copy

Join clips end to end. Dozens of GB in seconds, as long as the clips match.

Command

# list.txt — one line per clip, absolute paths, quoted
file '/footage/a.mp4'
file '/footage/b.mp4'

ffmpeg -f concat -safe 0 -i list.txt -map 0 -c copy -movflags +faststart out.mp4

Why it's written this way

  • -f concat the concat demuxer: reads packets from each file in turn and hands them to the muxer. Nothing is decoded.
  • -safe 0 allows absolute paths in the list. Without it, anything outside the working directory is "unsafe" and refused.
  • -c copy works only because every clip's streams are byte-compatible. That is a precondition, not something ffmpeg checks for you.

Breaks when

  • Any clip differs in codec, resolution, fps, pixel format, audio codec, sample rate, or channel count. You get a file that plays wrong (frozen video, drifting audio) or a muxer error. Probe first and refuse.
  • One clip has no audio and the others do. The demuxer can't cope with a stream appearing and disappearing. Fix: give the silent clip a silent track with the video copied (see Normalize). Don't re-encode the video for this.
  • A clip is variable frame rate. Concat-copy works mechanically but the result drifts. Normalize that clip to CFR once.
  • Timestamps don't start at zero in some clips (common after copy-trims without make_zero). The join stutters. Re-trim with make_zero, or remux each clip with -fflags +genpts.

The wrong way

ffmpeg -i a.mp4 -i b.mp4 -i c.mp4 -filter_complex "[0][1][2]concat=n=3:v=1:a=1" out.mp4

That's the concat filter. It decodes and re-encodes every clip, every time, even when they already match. It exists for joining clips that genuinely differ, and even then the better move is to normalize only the odd one out and then demux-copy the set.

ffkit: ffkit concat out.mp4 a.mp4 b.mp4 c.mp4 probes, refuses with a reason on mismatch, and --normalize fixes only the mismatched clips (video copy for audio-only problems).

Merge streams

copy

Video from one file, audio from another. Music under a timelapse, a clean audio recording replacing camera audio.

Command

ffmpeg -i video.mp4 -i music.m4a -map 0:v:0 -map 1:a:0 -c copy -shortest \
       -movflags +faststart out.mp4

# start the audio 1.5 s later than the video
ffmpeg -i video.mp4 -itsoffset 1.5 -i music.m4a -map 0:v:0 -map 1:a:0 -c copy -shortest out.mp4

Why it's written this way

  • -map 0:v:0 first video stream of the first input. Without explicit maps, ffmpeg picks "best" streams by its own rules and you may get the camera audio back.
  • -map 1:a:0 first audio stream of the second input.
  • -shortest stop when the shorter stream ends, so a three-minute track doesn't leave two minutes of black after a one-minute clip.
  • -itsoffset applies to the input that follows it. Positive delays that input.

Breaks when

  • The audio codec isn't allowed in the output container (e.g. FLAC or Opus into MP4). Re-encode the audio only: -c:v copy -c:a aac -b:a 192k.
  • You want to keep the original audio as a second track: add -map 0:a? (the ? means "if present").

ffkit: ffkit merge out.mp4 --video v.mp4 --audio music.m4a [--offset 1.5] [--keep-original-audio]

Remux

copy

Change the container (MOV → MP4, MKV → MP4) without touching the streams. Also the first thing to try on a file that won't play right.

Command

ffmpeg -i in.mov -map 0 -c copy -movflags +faststart out.mp4

# HEVC into MP4: tag it so Apple apps open it
ffmpeg -i in.mkv -map 0 -c copy -tag:v hvc1 -movflags +faststart out.mp4

# broken timestamps: regenerate them
ffmpeg -fflags +genpts -i broken.mp4 -map 0 -c copy fixed.mp4

Why it's written this way

  • -tag:v hvc1 ffmpeg writes HEVC as hev1 by default; QuickTime and Final Cut want hvc1. Same bytes, different label.
  • -fflags +genpts rebuilds presentation timestamps from the packet order. Fixes "non-monotonic DTS" and files that seek badly, without decoding anything.

Breaks when

  • The target container doesn't support a stream's codec (PCM audio or MJPEG into MP4, for instance). Re-encode that stream only.
  • MKV subtitles into MP4 need -c:s mov_text, or drop them with -sn.

ffkit: ffkit remux in.mov out.mp4 [--fix-ts]

Timelapse

encode · once

Keep one frame in N, drop the audio, play it back at normal speed. This is the one step that has to decode. The job is to decode as little as possible and encode only the frames that survive.

Command (keyframe mode, when GOP = N)

ffmpeg -skip_frame nokey -hwaccel videotoolbox -i in.mp4 \
       -vf "setpts=N/(30*TB)" -r 30 -fps_mode cfr -an \
       -c:v h264_videotoolbox -q:v 60 -movflags +faststart out.mp4

Command (select mode, any N)

ffmpeg -hwaccel videotoolbox -i in.mp4 \
       -vf "select='not(mod(n,30))',setpts=N/(30*TB)" -r 30 -fps_mode cfr -an \
       -c:v h264_videotoolbox -q:v 60 -movflags +faststart out.mp4

Why it's written this way

  • -skip_frame nokey tells the decoder to discard every non-key frame before decoding it. If the source GOP is 30 and you want 1-in-30, you get your timelapse while decoding ~3% of the frames. Near copy speed.
  • select='not(mod(n,30))' keep frame n when n mod 30 is zero. Decodes everything, so use hardware decode. Works for any N and any GOP.
  • setpts=N/(30*TB) re-stamp the surviving frames so they play back consecutively at 30 fps instead of with 29-frame gaps.
  • -r 30 -fps_mode cfr force a constant output rate so the muxer writes clean timestamps.
  • -an no audio. Audio at 30× is noise; if you want it, atempo chains in ≤2× steps (ffkit's --keep-audio builds the chain).
  • -q:v 60 VideoToolbox quality knob (1–100). ~60 for delivery, ~75 for a mezzanine. On libx264 use -crf 23 / -crf 18.

Breaks when

  • GOP ≠ N and you use keyframe mode. Output speed follows the GOP, not your N. A 120-frame GOP gives a 120× timelapse whatever you asked for. Probe the GOP; fall back to select mode when it doesn't match.
  • You timelapse a timelapse, or re-encode the result afterwards. Two generations of loss and double the time. Do it once, on the original, then copy.
  • Variable frame rate source. mod(n,30) counts frames, not time, so the speed-up wobbles. Normalize to CFR first, or accept it.

The wrong way

ffmpeg -i in.mp4 -vf fps=1 frames/%06d.png
ffmpeg -framerate 30 -i frames/%06d.png -c:v libx264 out.mp4

Export every surviving frame as a PNG, then reassemble. Two full passes, a folder of lossless images the size of the original video, and the decoder still processed every frame on the way to fps=1. It's how every tutorial from 2013 does it, and it's five to fifty times slower than selecting in one pass.

ffkit: ffkit timelapse in.mp4 out.mp4 --every 30 --fps 30. Mode auto measures the GOP and picks keyframe mode when it matches.

Normalize

encode · once

The one permitted encode for sources that don't match: bring the odd clips to the first clip's codec, size, frame rate, and audio layout, so everything after is copy.

Command (video differs)

ffmpeg -hwaccel videotoolbox -i odd.mov \
       -vf "scale=1920:1080:force_original_aspect_ratio=decrease,pad=1920:1080:(ow-iw)/2:(oh-ih)/2,setsar=1" \
       -r 30 -fps_mode cfr -c:v h264_videotoolbox -q:v 75 \
       -c:a aac -b:a 192k -ar 48000 -movflags +faststart odd.mezz.mp4

Command (only audio differs)

# no audio track: add silence, copy the video
ffmpeg -i silent.mp4 -f lavfi -i anullsrc=r=48000:cl=stereo \
       -map 0:v:0 -map 1:a:0 -shortest -c:v copy -c:a aac -ar 48000 out.mp4

# wrong sample rate / codec: re-encode audio only
ffmpeg -i in.mp4 -map 0:v:0 -map 0:a:0 -c:v copy -c:a aac -ar 48000 -ac 2 out.mp4

Why it's written this way

  • scale … decrease + pad fit inside the target without stretching, letterbox the rest. setsar=1 clears odd sample-aspect tags that would make the concat refuse.
  • -r 30 -fps_mode cfr resample to a constant rate. This is also the fix for variable frame rate phone footage.
  • anullsrc a generated silent audio source. Pure muxing; the video packets are untouched.
  • -c:v copy on the audio-only variants, because pixels were never the problem.

Breaks when

  • You normalize every clip "to be safe". That's the concat filter with extra steps. Normalize only the clips the probe flagged.
  • Mezzanine for a long NLE edit: use ProRes (prores_videotoolbox -profile:v 2) instead of H.264; it's bigger but every later scrub and render is faster.

ffkit: ffkit normalize odd.mov odd.mezz.mp4 --fps 30 --width 1920 --height 1080, or let ffkit concat --normalize decide per clip.

The hard way, and when it's right

Copy-first is a default, not a law. These are the constraints that make a re-encode the correct answer. The rule for all of them: do it once, at the point in the pipeline where the most copy-only steps come after it.

ConstraintWhy copy failsDo this instead
Destination can't play the sourceWeb, a client's phone, a projector: stream copy gives a file nobody can open.Delivery encode, H.264 yuv420p + AAC, as the last step.
Frame-accurate cutCopy snaps to keyframes; a 2 s GOP can miss by 2 s.trim --exact: fast seek, decode, re-encode only that clip.
Mismatched sources into one concatThe demuxer can't join different codecs or rates.Normalize only the odd clips to a mezzanine, then demux-copy.
Variable frame rateConcat drifts, timelapse wobbles, NLEs misbehave.One pass to CFR (-r N -fps_mode cfr), then copy forever.
Any filter: timelapse, scale, overlay, speed, colourTouching pixels is decode + encode by definition.One pass, on the original, hardware decode and encode.
A master for a long editH.264 is cheap to store and expensive to scrub.Encode once to ProRes; every scrub, render, and export after is fast.
Broken fileCorrupt timestamps, missing index, odd stream.remux --fix-ts first; full re-encode only if that fails.

ffkit

the toolkit

Everything above, as commands that probe first, copy by default, dry-run, log, and verify. Built so a coding agent can't drift back to re-encoding everything.

ffkit probe     clip1.mp4 clip2.mov
ffkit trim      in.mp4 out.mp4 -s 0:10 -e 1:20 [--exact]
ffkit concat    out.mp4 a.mp4 b.mp4 c.mp4 [--normalize]
ffkit merge     out.mp4 --video v.mp4 --audio music.m4a
ffkit remux     in.mov out.mp4 [--fix-ts]
ffkit timelapse in.mp4 out.mp4 --every 30 --fps 30
ffkit run       jobs/beach.yaml        # -n = dry run, --force = redo
ffkit caps                             # what this machine's ffmpeg can really do

A job file

name: beach-day
workers: 4
steps:
  - op: each                 # parallel, one per file
    inputs: ["src/*.MP4"]
    do: { op: timelapse, output: "work/{stem}_tl.mp4", every: 30, fps: 30 }
  - op: trim
    input: src/intro.MP4
    output: work/intro.mp4
    start: "0:05"
    end: "0:45"
  - op: concat
    inputs: ["work/intro.mp4", "work/*_tl.mp4"]
    output: out/final.mp4
    normalize: true          # fixes only the clips that need it
  - op: merge
    video: out/final.mp4
    audio: music/track.m4a
    output: out/final_music.mp4

Outputs that already exist and verify are skipped on re-run, so a job that died halfway picks up where it stopped. Every run writes a log with each command, its exit code, and its time.

The rules the agent follows live in AGENTS.md in the same repo, written as constraints: copy first, -ss before -i, probe before concat, audio problems never re-encode video, one encode per pipeline, verify every output.

Keyframe-aligned copy trims, demuxer concat, keyframe-only decode for timelapses, and audio-only fixes are the four tricks that account for most of the speed. Everything else is knowing when you're allowed to break the rule.
